# 上下文节省

目标是在不丢失用户意图、约束、证据和下一步的前提下，减少无关输出、重复读取和冗长记录。

## 开始任务

- 先提取 `current goal`、范围、验收标准、不可变约束和已知状态。信息不足时做最小合理假设，并记录该假设。
- 先检查工作区入口和适用指令，再用 `rg` 或 `rg --files` 定位符号、文件和调用点；不要先倾倒整个目录或大文件。
- 为长任务维护一份短状态，只保留：

  ```text
  current goal
  completed work
  important decisions
  unresolved issues
  next step
  ```

  状态变化时才更新；不要复制对话、完整日志或已经理解的代码。

## 检索和工具输出

- 搜索优先、读取最小范围：先看文件名、匹配行、符号和调用关系，再读取相关实现及必要的相邻行。
- 未知或可能很大的命令默认限流，例如 `COMMAND 2>&1 | head -c 4000`；日志和测试输出优先筛选失败、警告及末尾摘要。
- 只在当前决策需要时扩大读取范围。已经理解且未变化的文件不要重复读取；编辑后只重新检查受影响的片段。
- 独立的只读搜索可以并行；有依赖关系的命令按顺序执行，避免重复扫描同一目录。
- 原始输出只用于当下判断；将路径、符号、失败原因和证据位置压缩进状态，不要保留整段输出。

## 实现和验证

- 一次聚焦一个明确子任务，先界定受影响文件和接口不变量，再做最小补丁；不要借机混入无关重构。
- 按改动风险逐级验证：局部语法或 lint → 定向单元测试 → 模块测试 → 集成或完整测试。只有共享接口、架构或发布要求变化时才扩大范围。
- 失败时只读取第一个相关失败及其必要上下文，区分代码缺陷、配置问题和环境阻塞；修复后仅重跑受影响检查。
- 不把阅读代码当作测试通过的证据，也不编造未执行的结果；最终只报告实际修改、实际检查和仍未解决的问题。

## 上下文压缩

当上下文开始膨胀时：

1. 暂停继续读取，先把已知事实写入五项短状态。
2. 删除重复输出、过时假设和已解决分支，只保留当前决策所需信息。
3. 保留精确路径、行号或符号、用户约束、失败证据和风险；不要为了变短而删掉未解决问题。
4. 从 `next step` 继续，不要从头重新探索。

## 边界

- 节省上下文不能弱化安全、隐私、权限、数据完整性或用户明确的格式要求。
- 用户明确要求完整文件、日志、差异或逐字内容时，按要求输出；默认限流只适用于未指定范围的探索性输出。
- 摘要是导航，不是证据；需要作出关键结论时回到对应的最小源片段。
